# Dynamic Waters River Guard

Dynamic Waters の山岳河川づくりを**サーバスレッドから外す**当部MOD（サーバ専用）。

調査の全文は [worlds/world-3/mod-notes/dynamicwaters.md](../../mod-notes/dynamicwaters.md)。

## 何を直したか

参加すると**サーバスレッドが3分前後まるごと止まり**、部員からは
「キャラが落下し続け、やがてタイムアウトする」ように見えていた。

Dynamic Waters は `ChunkWatchEvent.Watch` の中で、見えたチャンクの周り
**±2 リージョン（1リージョン＝256ブロック四方）**の山岳河川を**同期で**引き直す。
参加時は視界ぶんのチャンクが一斉に発火するので、**約36リージョン**を
プレイヤーを配置する前に作りきることになる。
記録はメモリ上にしか無いので**再起動のたびに冷え、最初に入った1人が全員ぶんを肩代わりする**。

## 実測（本番ワールド world3・RCON の応答遅れで測定）

| 構成 | サーバが塞がった時間 |
| - | - |
| 素のまま（記録が冷えている） | **231,451ms** |
| 素のまま（記録が温まっている） | 7,909ms |
| `enableMountainRivers = false`（機能を捨てる） | 0ms |
| **本MOD 1.0.0**（`onChunkWatch` を非同期化） | ログインは即時／**参加直後に 141,599ms** |
| **本MOD 1.1.0**（＋毎tickの水流を止める） | **26,518ms** |
| **本MOD 1.3.0**（＋無人時の掃き出し） | 下記「測り方」で再測 |

## 3つの手当て

| どこ | 何をしたか |
| - | - |
| `DynamicWaters$ModEvents.onChunkWatch` | mixin で中止し、同じ仕事をワーカースレッドで行う。できたぶんからパケットを送る |
| `HydrologyManager.getRiverFlow` | `cachedOnly` を強制的に `true` に。**専用サーバでは `false` を渡す**作りで、毎tick その場で作りにいっていた |
| サーバ起動時 | ワールドボーダーの内側を**リングの順に掃いて記録を埋める**。**人が居る間は止まる**（Chunky Autopause と同じ約束） |

⚠ **わざと触っていない**: `calculateRiverCarving` / `isNearRiver` / `isTooCloseToRiver`。
同じ重い計算に入るが**地形を彫る側**で、短絡すると**生成される地形が変わる**。
ワーカースレッドで走るので、掃き出しで記録を先に埋めておけば速い。

## ⚠ 掃き出し（無人時の先読み）を「要らない」と思ったら、まずここを読む

> ## ⚠⚠ 訂正（2026-08-05・同日中）
>
> **下の「Chunky が 4.7〜6.0 → 0.5 チャンク/秒 に落ちる」は誤り。取り消す。**
> ログ全体を数え直すと、**掃き出しがある側のほうがむしろ遅かった**:
>
> | | 参加前の Chunky（cps） | 参加 |
> | - | - | - |
> | 掃き出し無し（2.0.0） | 76.3 / 7.5 / 0.3 / 8.4 / 6.0 | 41秒 |
> | 掃き出しあり（1.3.0） | 1.6 / 1.6 / 12.3 / 2.2 / 1.7 / 1.3 / 1.9 / 4.7 | 即時 |
>
> 元の数字は**都合のいい2行ずつを拾ったもの**だった。さらに、比べた2回は
> **ボーダーが 1719 と 3936**・事前生成量が **19,784 と 60,811 チャンク**と条件が違い、
> **A/B として成立していない**。
>
> **確かなのは2つだけ**: 1.3.0 では参加が即時だった（20分の観測で遅れ0回）。
> 2.0.0 では 41,099ms 止まった（1回・条件違い）。**なぜ止まったかは未解明。**
>
> ⚠ **この節の機序を根拠に設計を決めないこと。** 決めるなら、
> **同じボーダー・同じ事前生成量で、jar だけ入れ替えて測り直す**。


**2026-08-05 に「理屈で要らない」と判断して外し、実測で41秒に戻した。**

掃き出しの役目は「流れの先読み」ではなく、**Chunky（事前生成）の下ごしらえ**。
外すと Chunky 自身が生成のたびに9秒級のリージョン計算を負い、生成が10分の1に落ちる。
参加時の `getChunkBlocking` はその後ろに並ぶので、参加が41秒に戻る。

| 構成 | Chunky の生成速度 | 参加 |
| - | - | - |
| 掃き出しあり（1.3.0） | **4.7〜6.0 チャンク/秒** | 即時 |
| **掃き出し削除（2.0.0）** | **0.5 チャンク/秒** | **41,099ms・1回目はタイムアウト** |

⚠ **どちらの回も Chunky は動いていた。** Autopause は「入り終わってから」止めるので、
入れないでいる間は止まらない。条件は揃っている。

外すときに立てた筋は3本とも通っていたのに、結論は誤りだった:

1. 「ボーダーが未生成の場所を塞ぐから彫る処理は走らない」→ **走る。Chunky が前線で焼いている**
2. 「流れに即時性は要らない」→ **正しい。だが掃き出しの役目はそこではない**
3. 「Chunky と二重で無駄」→ **逆。1リージョンを1回計算し、その中の約256チャンクで使い回す**

## 残っている課題: キャッシュ上限

`MOUNTAIN_REGION_CACHE` は 2048 リージョンしか持たない。

| ボーダー直径 | 掃くリージョン数 | |
| - | - | - |
| 3,936（2026-08-05 時点） | 289 | 上限内 |
| 24,320（目標） | **9,409** | **上限超。掃いた先から追い出す** |

⚠ **上限を付けるだけでは解決しない**（外側が冷えるので遅さが移動するだけ）。
役目が Chunky の下ごしらえである以上、**掃くべきは Chunky がいま焼いている前線**。
⚠ **設計を変えるときは、あり/なしを同じ条件で1回ずつ測る仕掛けを先に作ること。**

## 測り方（再現手順）

1. `dev/server-play` を**再起動**する（記録が温まっていると差が出ない）
2. 起動ログの `River Guard: sweep finished` を待つ（無人時のみ進む）
3. RCON へ1秒おきに `list` を撃ち、応答が返るまでの時間を記録する
   （**RCON はサーバスレッド上で実行されるので、塞がった時間がそのまま出る**）
4. **人が参加する**（⚠ `online-mode=true` なので自動確認クライアントは使えない）

**山岳河川が残っているかの確認**は `/locate_river_terrain`。
このコマンドは**キャッシュ参照のみ**（`cachedOnly=true`）なので、
「見つかる＝ワーカーが実際に組んで記録に入れた」の証拠になる。

## 版で縛っている理由

`mods.toml` は `dynamicwaters` を `[11.1,12)` に縛っている。
本MODは `onChunkWatch` を中止するので、**Dynamic Waters 自身の `SENT_REGIONS` が空のまま**になる。
11.1.x では `onChunkWatch` と `onPlayerLogout` しか読まないので無害だが、
**上げるときはそこを読み直すこと**。
